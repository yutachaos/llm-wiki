# Backstage導入ガイド（Earthly）

- 出典: [earthly.dev の記事](../../sources/backstage-adoption-guide.md)。20以上の組織の知見を統合した実践ガイド

## 要点

### 概要

SpotifyのBackstageはOSSの社内開発者ポータル（IDP）フレームワークで、市場シェア67%とされる。サービスカタログを中核に、Scaffolder（テンプレートによるサービス標準作成）、Plugins（スコアカード・セキュリティチェック等）、TechDocs（コード隣接型ドキュメント）を提供する。

### 向いているケース

- チーム・サービス数が多く「スケールの痛み」を抱える組織
- 専任3〜5名のエンジニア（フロントエンド/React/TypeScript経験者を含む）を割ける
- 経営層のスポンサーシップとトップダウンの導入合意がある
- 6〜12ヶ月の導入期間を許容できる
- 新規サービス中心（レガシーの後付け移行が主目的でない）

### 向いていないケース

- 30〜40名未満のスリムな組織
- プラットフォームチームにフロントエンド/TypeScriptの知見が皆無
- 「すぐ使えるプロダクト」を期待している
- 経営層の後ろ盾がない
- 既に定着した競合システムがある

### コスト構造（「無料OSS」神話への反証）

- 3名体制の自前実装（中規模組織）: 年間 $380K〜650K（エンジニア人件費＋インフラ/SRE運用＋フロントエンド育成/採用）
- フルマネージドSaaS: 約$84K/年（200名エンジニア、$35/dev/月換算）
- ハイブリッド（1〜2名＋有償プラグイン）: $150K〜250K/年

### よくある失敗

1. **人員不足・スキルギャップ**: 130ユーザーを1名で支えたケースでは、カタログ保守以上のプラグイン開発に手が回らなかった。React/TypeScript経験者不在がボトルネックに
2. **ドキュメント対象の過剰拡大**: デザイナーやPMなどエンジニア以外はMarkdown/GitHubワークフローに抵抗し、Confluenceを使い続けた
3. **100%導入を追い求める**: 全社導入を狙うとレガシーサービスの移行にリソースを消耗する。成功しているのは80%カバレッジを目標にするケース
4. **経営層のスポンサーシップ欠如**: 「作れば使われる」という前提は失敗する。トップダウンの合意と投資なしに自然採用は稀

### 成果指標の例

- オンボーディング速度: 新入社員の初回PRまでの日数（14日→5日）
- サービス立ち上げ: テンプレートでのデプロイ（4〜6週間→60秒）
- 開発者体験スコア: DXスコア（6.4→8.1）
- インシデント対応: MTTR（90分→55分）
- DORAメトリクス: デプロイ頻度30%増、リードタイム25%減
- ドキュメント効率: 組織全体で年間約2FTE分の工数削減
